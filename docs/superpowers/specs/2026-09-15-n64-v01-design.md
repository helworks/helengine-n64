# N64 v0.1: native host and unlit cube — draft design and milestone plan

**Status:** Draft for discussion. No implementation started.

**Goal:** Build a standalone Helengine N64 ROM that initializes video and reliably renders a rotating, unlit cube.

**Confirmed scope:** Native host and cube first. Helengine editor, generated runtime, scene export, and platform-builder integration belong to a subsequent milestone.

## Reference intake

Read both project references: [Nintendo 64 Development Reference](../../Nintendo_64_Development_Reference.md) and [N64 Rendering Optimization](../../N64_Rendering_Optimization.md).

The development reference supplies the bootstrap, build, memory ownership, video, and debugging baseline (sections 2–8, 10, and 14–15). The optimization reference supplies the framebuffer arithmetic, explicit render state, and asynchronous resource-lifetime constraints (sections 5–6 and 10–11).

The broader recommendations on assets, visibility, batching, profiling, audio, and custom microcode are future guidance. They are not prerequisites for this cube milestone.

The documents identify libdragon `39d0d6096130836a65710da6730290701d060272` and Tiny3D `73d822f3af7c85cc1b93eaa4546504ba0a4ea156` as inspected snapshots, explicitly not a tested compatibility pair. Use them as candidate pins. Verify availability and build compatibility before adopting them; record any replacement and its reason. The exact pinned source files were subsequently fetched through the shell during implementation-plan preparation; build compatibility remains untested. The live [Tiny3D README](https://github.com/HailToDodongo/tiny3d) confirms the preview dependency, RDPQ integration, and persistent matrix/vertex requirements, but does not establish compatibility of those specific pins.

## Approach

**Recommended: C++ native host using libdragon RDPQ and Tiny3D.** libdragon handles startup, diagnostics, video surfaces, and presentation; Tiny3D handles geometry transforms and clipping. Supply original cube geometry directly, avoiding an asset importer or ROM filesystem dependency for v0.1.

Alternatives considered:

- **libdragon OpenGL:** potentially useful when porting an existing fixed-function GL renderer. This initial host has no GL renderer to preserve, so that compatibility layer brings little benefit here.
- **CPU transforms plus direct RDPQ triangles:** can draw a cube, but makes projection and clipping our responsibility before proving the platform integration. Keep Tiny3D's geometry path instead.

## Visible result and limits

- Standard 320 × 240 video, 16-bit color, two display buffers, one 16-bit depth surface.
- Target the base 4 MiB console; no Expansion Pak requirement, save device, controller, USB connection, or external asset dependency.
- Fixed perspective camera with a centered cube rotating slowly about two axes.
- Six distinct opaque face colors; no textures, lights, fog, or blending. Colors remain constant as faces turn. Duplicate face vertices as needed: 24 vertices and 12 triangles are sufficient.
- Backface culling, depth tests, depth writes, and color/depth clears enabled explicitly. Preserve Tiny3D's clipping path.
- Advance rotation using elapsed time, with a bounded delta after debugger pauses. Do not tie angular speed to 50/60 Hz presentation.
- Start with RDP antialiasing disabled and explicit SDK VI filter/gamma settings; record those settings with validation. Image-quality tuning is outside this milestone.

Two color surfaces and one depth surface consume 460,800 bytes (450 KiB) before alignment and SDK overhead. Measure executable, heap, stacks, and SDK allocations instead of treating this as the total footprint.

## Native structure

Follow the inspected sibling convention: a small `src/main.cpp` delegates to a platform host under `src/platform/n64/`. Use namespace `helengine::n64` and focused files with documented responsibilities.

| Proposed file | Responsibility |
|---|---|
| `src/main.cpp` | Construct the native host and enter its loop. |
| `src/platform/n64/Nintendo64BootHost.hpp/.cpp` | Ordered startup, elapsed time, diagnostics, and top-level frame loop. |
| `src/platform/n64/Nintendo64Video.hpp/.cpp` | Display/depth allocation, acquisition, clearing, completion, and presentation. |
| `src/platform/n64/Nintendo64RasterRenderer.hpp/.cpp` | Tiny3D initialization, camera, model matrix, explicit unlit state, and cube submission. |
| `src/platform/n64/Nintendo64CubeMesh.hpp/.cpp` | Persistent original cube vertices and triangle indices. |
| `Makefile` | SDK build integration and explicit source/dependency list; emit ROM, ELF, and map. |
| `scripts/build.ps1`, `scripts/launch_in_emulator.ps1` | Windows entry points with explicit tool/emulator paths and propagated failures. |
| `docs/Build.md`, `docs/Validation.md` | Reproducible environment instructions and observed acceptance results. |

These are proposed boundaries, not new shared engine interfaces. Do not copy the mature sibling builders or introduce placeholder services. Keep dependency versions in a checked-in manifest; keep SDK installations and build output out of source control. Select one supported host build environment during setup, following the sibling Docker workflow if available, rather than implementing Docker, WSL, and MSYS2 support together.

## Frame ownership and rendering sequence

1. Initialize debug output, display, RDPQ, depth storage, and Tiny3D in their required order. Check resource allocations before entering the loop.
2. Allocate geometry and matrix storage once, with the SDK-required alignment and cache visibility. Cube geometry remains immutable for the run.
3. Acquire the next display surface. Update the model transform only after the previous frame's graphics completion has been established.
4. Attach color/depth targets, start the Tiny3D frame, configure the camera/viewport, and clear both targets through SDK helpers.
5. Set opaque unlit vertex-color state, depth behavior, and winding explicitly; submit the cube and required triangle synchronization.
6. Complete rendering and present using a documented SDK completion/presentation combination. Verify the exact calls against the selected headers. The first implementation waits once per frame before allowing mutable resources to be reused.

Display-buffer rotation alone does not prove a matrix is safe to overwrite. Uncached memory alone does not prove the device has finished reading it. Keep this conservative ownership policy explicit; asynchronous frame arenas and retained command blocks are deferred.

Startup failure should produce a specific diagnostic and stop rendering safely. If video is already usable, show a simple failure indication. Log initialization checkpoints and the first completed frame; avoid continuous per-frame output in the normal build.

## Milestone plan

### 1. Reproducible toolchain and video bootstrap

- [ ] Inspect the available host toolchain/container and emulator, then choose one supported build route.
- [ ] Resolve and record compiler, libdragon, and Tiny3D revisions; build the selected upstream minimal example to verify the combination.
- [ ] Add the native entry point, host, video module, build files, and bounded startup logs.
- [ ] Produce `helengine_n64.z64` plus an unstripped ELF and map. Keep ROM checksum and tool versions with the build record.
- [ ] Boot a clear-color screen in ares Homebrew mode and verify repeated presentation. A failing compiler/build command must not launch an old ROM.

**Checkpoint:** A fresh build produces a bootable video-only ROM with identifiable startup and first-frame diagnostics.

### 2. Static unlit cube

- [ ] Add persistent cube geometry and the narrow renderer module.
- [ ] Establish coordinate convention, vertex winding, camera projection, and Tiny3D matrix conversion using the selected upstream example.
- [ ] Render the fixed-pose cube with explicit face colors, depth, and culling; no lighting contribution.
- [ ] Test multiple fixed camera/cube poses, including reversed triangle submission order to demonstrate depth correctness rather than accidental ordering.

**Checkpoint:** The visible faces and occlusion are correct at all diagnostic poses, and the debug RDPQ validator reports no command/state errors.

### 3. Rotation and lifetime validation

- [ ] Add time-based two-axis rotation and the conservative completion-before-reuse policy.
- [ ] Exercise the cube across the near plane and screen edges using diagnostic camera poses, retaining proper clipping.
- [ ] Run for ten minutes with repeated rotations; check for hangs, flicker, corrupted vertices, or memory growth. Allocate no frame-loop resources after initialization.
- [ ] Check approximately 50 Hz and 60 Hz modes for equal rotation speed; record the modes actually exercised.

**Checkpoint:** Stable animation and resource use, including after a debugger pause; no performance claims inferred from host emulator FPS.

### 4. Package and record acceptance

- [ ] Verify a clean rebuild and clear failures for missing SDK/emulator configuration.
- [ ] Record ROM hash, source/dependency revisions, video settings, memory evidence, emulator version, and test results.
- [ ] Cold-boot and reset the same ROM on a 4 MiB console when hardware is available; also check launch without USB. Test with an Expansion Pak if available.
- [ ] Keep emulator completion and hardware verification as separate recorded statuses. Lack of hardware leaves hardware acceptance pending.

**Checkpoint:** Reproducible standalone artifact, instructions another developer can follow, and explicit evidence for each tested configuration.

## Deferred work

Generated C++ runtime integration, platform registration and C# builder, authored scene loading, DragonFS packaging, textures/material cooking, input APIs, audio, saving, physics, UI, scene graphs, visibility systems, detailed RSP profiling, asynchronous frame arenas, and custom microcode.

The next milestone should route one authored Helengine camera, cube mesh, transform, and unlit material through the existing build pipeline into this working host. That follow-up will need a separate compatibility and memory assessment of the generated runtime.
